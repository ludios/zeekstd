# Standard-tool interop test of zeekstd output (2026-09-16)

Question tested: can the standard zstd tools decompress everything zeekstd writes?
Tested against `zstd` 1.5.7 CLI (`zstd -d`, `zstd -t`, `zstd -l`, `zstdcat`), `pzstd` 1.5.7,
Meta's reference seekable decoder (zstd `contrib/seekable_format`, via `zstd-safe` feature
`seekable`), and zeekstd's own decoder. Branch `frame-size-0` at `06f093f`, release CLI build.
Scripts, raw results and the library probe crate are in [interop-2026-09-16/](interop-2026-09-16/).
Every check compares SHA-256 of the decoded stream with the original input.

## Result

Every archive that does not use `--patch-from` decoded correctly with every tool, byte for byte.
Frame counts, per-frame sizes and random-access reads also agreed with the reference decoder.

| Suite | Archives | Checks passed | Checks failed | Failures |
| --- | ---: | ---: | ---: | --- |
| CLI matrix (`cli_interop.sh`) | 45 | 252 | 11 | all `--patch-from` |
| Large files (`big_interop.sh`) | 5 | 39 | 8 | all `--patch-from` |
| Library API probes (`libtest/`) | 14 | 41 + 12 reference-decoder | 1 | pzstd has no dictionary support |

Covered on the write side: sizes 0, 1, 96 B, 1 KiB, 1 MiB, exactly 2 MiB, 2 MiB + 1, 6 MiB
(3 exact frames), 10 MiB mixed, 64 MiB zeros, 3 GiB with 512 KiB frames (6144 frames),
5 GiB + 1 random with 2 MiB frames (2561 frames, compressed and uncompressed offsets past 4 GiB),
`-s 3G` (capped to the 1 GiB max frame), frame sizes 1 B and 1 KiB, both frame-size policies,
levels 1, 3, 9, 19, 22, checksums on and off, stdin to stdout, detached Head-format seek table,
Head table appended after the data, `RawEncoder` with 1-byte and 7-byte output buffers and
1-byte and 3-byte seek-table buffers, manual and empty frames, 102400 one-byte frames,
`BufWriter` with mid-stream `flush()`.

## `--patch-from` archives and the zstd CLI

zeekstd re-applies the prefix to every frame. The zstd CLI's `--patch-from` decompression
references the prefix once (single-use `ZSTD_DCtx_refPrefix`), so it decodes the first frame and
then fails with `Data corruption detected`. This is a zstd CLI limitation, not a bad archive.

| Archive | `zstd -d --patch-from=P` | `zstd -d -D P` |
| --- | --- | --- |
| single frame, prefix ≤ 128 MiB | works | works if P ≤ 32 MiB |
| single frame, prefix > 128 MiB | needs `--memory=<window>` or `--long=<log>` because zeekstd sets the window to the next power of two above the prefix size | refused: `-D` rejects dictionary files above 32 MiB |
| multi-frame, prefix ≤ 32 MiB | first frame only, then error | works, verifies checksums |
| multi-frame, prefix > 32 MiB | first frame only, then error | refused |

So a multi-frame patch archive with a prefix over 32 MiB can only be restored by zeekstd itself
or by custom libzstd code. `pzstd` does not support dictionaries or prefixes at all.
A prefix under 512 bytes makes the CLI fail before writing (`Parameter is out of bound`,
finding 17 in [astra.md](astra.md)).

## Integrity checks that were reproduced

- `zeekstd d` accepted a corrupted archive with exit 0 when the frame trailer lands exactly on
  the decoder's 131075-byte input-buffer boundary (finding 1 in [astra.md](astra.md)):
  131066 random bytes, default CLI options, payload byte 100 flipped. `zstd -t` rejected it.
- The same flip in a 10 MiB archive was caught by both tools.
- An archive truncated by 100 bytes was rejected by both tools (zeekstd fails to parse the table).
- `--no-checksum` archives cannot be verified by anything after a flip, as expected.
